# rtcstats-dashboard — Design

Date: 2026-08-26
Status: approved (design), pending implementation plan

## Purpose

A self-hosted post-mortem analysis dashboard for the standalone rtcstats deployment.
A support engineer picks a past session and learns why it went wrong, without reading
raw getStats.

This is the layer that `rtcstats.com` provides as a hosted service, built to run against
the local Postgres + MinIO stack in `rtcstats_docker_deployment`.

Non-goals: live monitoring of ongoing calls, fleet-wide trend analytics, and replacing
`dump-importer` as a standalone file viewer.

## Context

The existing deployment provides:

- `rtcstats-server` writes each dump to MinIO and a row to `"rtcstats-server"`
  (`id bigint`, `blob_url`, `session_start`, `session_end`, `rtcstats_user`,
  `rtcstats_conference`, `rtcstats_session`, `host_identifier`,
  `features_processing_start/stop`).
- `rtcstats-features` extracts features into `features_metadata`, `features_client`,
  `features_connection`, `features_track`, keyed by `dump_id` / `connection_id`.
- `rtcstats_analysis` and `rtcstats_observations` already exist in the schema. They are
  the landing zone for results returned by rtcstats.com for forwarded dumps. The
  dashboard does not write to them; it mirrors their shape.
- `dump-importer` and `packages/rtcstats-features` (MIT, ESM) contain the dump-parsing
  logic this project reuses rather than reimplements.

Design volume: thousands of dumps per day. Diagnostics are therefore precomputed, not
computed on view: the session list must be sortable worst-first without opening sessions.

## Decisions

| Decision | Choice |
|---|---|
| Data source | Server-backed: Postgres for the session list and features, MinIO for dumps |
| Diagnostics | Rules layer over `features_*`, precomputed by a worker |
| Evidence | Charts parsed from the raw dump in the browser |
| Stack | Node/TypeScript backend, React + Vite + uPlot frontend |
| Auth | Shared password from env, signed HTTP-only session cookie |
| Charts | uPlot (permissive licence). Not Highcharts, which `dump-importer` uses and which is not free for commercial use |
| Deployment | One image, one service added to the existing `docker-compose.yml` |

## Architecture

Four pieces in one repository:

1. **`rules`** — a pure library. Feature tree in, observations out. No IO, no database,
   no network. Imported by the worker.
2. **`analyzer`** — the worker. Polls Postgres for dumps whose features are done and
   which have no analysis row, runs the rules, writes scores and observations. Claims
   work with `SELECT ... FOR UPDATE SKIP LOCKED`, so N replicas are safe. Polls every
   10 seconds by default (configurable), in batches of 100 dumps. Also runs one-shot for
   backfill (`--from`, `--dump-id`, `--rules-version`, `--force`); `--force` is the only
   mode that re-processes rows already marked `failed`.
3. **`api`** — Fastify. Read-only against Postgres, plus a dump-streaming endpoint that
   proxies MinIO. Serves the built frontend in production. Does not analyse.
4. **`web`** — React + Vite. Two screens: session browser and session detail.

```
              +--------------+        +-------------+
   browser -->|  api (+web)  |------->|  Postgres   |<-- rtcstats-server
              +------+-------+        +------^------+    rtcstats-features
                     | dump stream           | scores + observations
                     v                       |
              +--------------+        +------+-------+
              |    MinIO     |<-------|   analyzer   |
              +--------------+ (only  |    (1..N)    |
                            if chart  +--------------+
                            bundles are added later)
```

The dashboard is read-only against rtcstats' own tables. It owns exactly one migration
(its two tables) and never writes to `"rtcstats-server"` or `features_*`, so an upstream
rtcstats upgrade cannot be broken by it and `script/import-schema.sh` keeps working
unchanged.

Under this design the worker reads only `features_*` and never opens a dump. The
MinIO link from the analyzer appears only if precomputed chart bundles are added later
(see Future work).

## Data model

The dashboard owns two tables whose columns deliberately parallel
`rtcstats_analysis` / `rtcstats_observations`, so the UI renders local and hosted
analysis through one mapper.

```sql
create table dashboard_analysis (
  id                 bigint generated by default as identity primary key,
  dump_id            bigint not null unique
                       references "rtcstats-server"(id) on delete cascade,
  created_at         timestamptz not null default now(),
  rules_version      text not null,
  status             text not null default 'ok',   -- 'ok' | 'failed' | 'insufficient_data'
  error              text,
  session_start      timestamptz,                  -- copied from features_metadata
  duration           integer,
  rtcstats_user      text,                         -- copied from "rtcstats-server"
  rtcstats_conference text,                        -- copied from "rtcstats-server"
  experience_score   real,                         -- 0..100, null unless status = 'ok'
  audio_score        real,
  video_score        real,
  connectivity_score real,
  observation_types  text[] not null default '{}', -- denormalized, for list filtering
  worst_severity     text,                         -- 'critical' | 'warning' | 'info' | null
  observations_count jsonb not null default '{}'   -- {"critical":2,"warning":5,"info":1}
);

create table dashboard_observations (
  id            bigint generated by default as identity primary key,
  analysis_id   bigint not null references dashboard_analysis(id) on delete cascade,
  pid           text,             -- connection_identifier; null = session-level
  type          text not null,    -- rule id, e.g. 'ice.slow_connect'
  severity      text not null,    -- 'critical' | 'warning' | 'info'
  category      text not null,    -- 'connectivity' | 'audio' | 'video' | 'device' | 'api'
  first_seen_at double precision, -- seconds from session start
  observation   jsonb not null    -- measured values, thresholds, evidence hints
);

create index on dashboard_analysis (session_start desc, experience_score);
create index on dashboard_analysis (rtcstats_user, session_start desc);
create index on dashboard_analysis (rtcstats_conference, session_start desc);
create index on dashboard_analysis using gin (observation_types);
create index on dashboard_observations (analysis_id);
```

Rationale for the three non-obvious choices:

- **One row per dump**, replaced on re-analysis rather than versioned. `rules_version`
  records which rules produced it, so a backfill is "re-run everything whose
  `rules_version` differs from current" with no history to de-duplicate in the list query.
- **`session_start`, `duration`, `rtcstats_user`, `rtcstats_conference` and
  `observation_types` are denormalized** into the analysis row. The list query — worst
  calls in a date range, filtered by problem type or by user — must be one indexed scan
  of one table at thousands of dumps a day, with no join to `"rtcstats-server"` or
  `features_metadata`. The copied values cannot diverge, because the source rows are
  immutable once feature extraction finishes.
- **`status` / `error` make failure terminal.** A dump the rules choke on gets
  `status='failed'` and is never picked up again, and broken dumps are queryable.

The `observation` JSONB payload is per-rule: measured value, threshold crossed, and the
evidence pointer (chart id plus time range). It is validated in the rules library, not by
the database.

## Rules layer

```ts
interface Rule {
  id: string;                                   // 'video.freezes'
  category: 'connectivity' | 'audio' | 'video' | 'device' | 'api';
  scope: 'session' | 'connection' | 'track';
  evaluate(ctx: RuleContext): Observation[];    // empty array = did not fire
}
```

`RuleContext` is the assembled feature tree for one dump — `metadata`, `client`,
`connections[]` each with `tracks[]` — plus the thresholds table. Rules never see the
database and never see each other's output.

**Rules emit data, not sentences:**

```json
{ "type": "video.freezes", "severity": "critical", "pid": "PC_2", "first_seen_at": 42.5,
  "observation": { "count": 14, "total_ms": 31200, "longest_ms": 8100,
                   "threshold": { "total_ms": 5000 },
                   "evidence": { "chart": "framesReceived", "from": 40, "to": 75 } } }
```

Human-readable text lives in the frontend, keyed by `type`. Rewording a message or
translating the UI therefore never requires re-analysing historical dumps; only a
threshold or logic change does.

**Scoring is subtractive and inspectable.** Each category starts at 100; every
observation subtracts severity weight times rule weight; the result is clamped to 0.
`experience_score` is a weighted mean over the categories that applied — a call with no
video track is not scored on video. All weights and thresholds live in one config file so
that tuning is a readable diff.

**Starter rule set** (all reading columns the existing migrations already added):

- *connectivity*: never connected; slow ICE connect; slow TURN gathering; ICE restarts;
  ICE restart followed by setRemoteDescription; null candidate added; relay-only path;
  DTLS role/handshake anomalies; clock skew; signaling and setLocal/RemoteDescription delays.
- *video*: freezes (count, total, longest); quality limitation CPU vs bandwidth
  percentage; resolution changes; slow time-to-first-frame; encode/decode time; hardware
  acceleration absent; null video decoder; QP degradation.
- *audio*: concealment ratio; jitter buffer flushes; time stretching; track ended
  unexpectedly.
- *device*: getUserMedia failures; low CPU performance; reload count.
- *api*: API failures.

Implement roughly a dozen first — never connected, slow ICE, freezes, quality
limitation, concealment and their neighbours explain most bad calls — then grow the
registry one file plus one fixture at a time.

**Versioning.** `RULES_VERSION` is a semver constant in the library, bumped by hand when
thresholds or logic change and stamped onto every analysis row. It is not derived from a
file hash: a refactor must not invalidate a million rows.

**`insufficient_data`** is a first-class status. A dump with no peer connection or no
getStats samples gets that status rather than a misleading score of 100.

## API

Read-only, cookie-authenticated, JSON.

```
POST   /api/login             { password } -> sets session cookie
POST   /api/logout
GET    /api/me                             -> { authenticated }

GET    /api/sessions          list + filters + keyset pagination
GET    /api/sessions/:dumpId  analysis + observations + feature tree + dump size
GET    /api/sessions/:dumpId/dump          streams the .json.gz from MinIO

GET    /api/rules             rule catalog (id, category, default severity) for filters
GET    /api/health            database and object-store reachability
```

`GET /api/sessions` filters on `from`/`to` (`session_start`), `user`, `conference`,
`types[]` (matched with `&&` against the GIN index), `severity` and `maxScore`. Sort is
`date` or `score`. Pagination is **keyset**, cursored on `(session_start, id)` or
`(experience_score, id)` — offset pagination degrades exactly where thousands a day
lives. The response carries only what the list renders: dump id, start, duration, user,
conference, scores, `worst_severity`, counts by severity, top three observation types.

`user` and `conference` are matched **exactly**, not fuzzily. They are free-text fields
the client sets and whose format is known. A trigram index can be added later if partial
matching turns out to be needed.

`GET /api/sessions/:dumpId` returns one composed object — analysis row, observations
ordered by severity then time, and the assembled feature tree — so the detail page can
render its verdict in one round trip, before the dump has downloaded. It also reports the
dump's size, which the frontend needs in order to warn before parsing a very large dump.

`/dump` proxies the bytes rather than redirecting to a presigned URL, so MinIO stays
entirely private and the browser authenticates with the same session cookie.
`Content-Length` is passed through so the UI can show real download progress.

Auth: a hash of the shared password in env, a signed HMAC cookie (`httpOnly`,
`sameSite=lax`, ~7 day expiry), a rate limit on login (10 attempts per IP per 15
minutes), and one middleware rejecting
everything else without a valid cookie. The built frontend is served by the same Fastify
process; there is no third container.

## Frontend

**Session browser.** A filter bar over a dense table. Filters default to the last 24
hours and are encoded in the URL, so any view is a link that can be pasted to a
colleague. Sort defaults to newest-first with a prominent worst-first toggle; both are
keyset-paginated behind a "load more". Each row shows time, duration, user, conference,
the experience score with a severity colour, and up to three observation-type chips.
Clicking a chip adds it to the filter.

**Session detail.** Three stacked regions sharing one x-axis:

1. *Header* — the four scores, session identity, client (browser, OS, CPU, memory), and
   a raw-dump download link.
2. *Verdict* — ranked observations grouped by severity, each expandable into a sentence
   rendered in the frontend from the `type` key plus the measured values, with a
   "show evidence" action.
3. *Evidence charts* — uPlot timeseries per connection and track, synchronized cursor,
   shared zoom. "Show evidence" zooms every chart to the observation's `from`/`to` and
   highlights the band.

Below the charts, an **event timeline strip** on the same x-axis shows ICE state
transitions, track added/removed, `getUserMedia` calls and signaling events. This is what
makes causality legible: a bitrate collapse landing exactly on an ICE restart is the
point of a post-mortem tool, and neither the feature table nor a chart alone shows it.

The verdict renders before the dump downloads: regions 1 and 2 come from the single
`/api/sessions/:id` call. Charts fill in once the dump has streamed and parsed. Parsing
runs in a **Web Worker** — `DecompressionStream('gzip')` feeding the `dump-importer`
parsing logic — so the UI never blocks; dumps above 25 MB compressed (configurable) ask
for confirmation before parsing rather than freezing a laptop. When a session has several peer connections, a selector switches between them and
the verdict stays visible, because observations are tagged with `pid`.

## Error handling

Failures are per-dump, never per-process. The worker wraps each dump in its own
try/catch: a dump that breaks the rules gets `status='failed'` with the error text and is
never retried, so one poison record cannot stall the queue. `FOR UPDATE SKIP LOCKED`
keeps replicas from colliding. Database and object-store outages back off and retry
rather than exiting. The worker logs structured JSON and tracks two numbers worth
alerting on: **analysis lag** (dumps with features done and no analysis row) and failure
count.

Two degradations are expected in normal operation:

- *Features not extracted yet*: `features_processing_stop IS NULL`, so the worker does
  not see the dump and the UI shows it as pending rather than as a good call.
- *Dump absent from MinIO while its rows remain in Postgres*: the near-certain result of
  any storage retention shorter than the database's. Verdict and observations still
  render from Postgres; the chart region reports "raw dump no longer in storage". The API
  returns a distinct status for this case so the frontend can tell it apart from a real
  failure.

The API connects as a **read-only role**: `SELECT` on `"rtcstats-server"` and `features_*`,
write rights only on the two dashboard tables. This makes "never writes to rtcstats'
tables" enforced by the database rather than by convention.

HTTP errors: 401 without a valid cookie, 429 on login rate limit, 404 for an unknown
dump, a distinct status for a dump missing from storage. No stack traces in responses.

## Testing

- **Rules library — fixture-driven unit tests, written first.** Per rule: fixtures that
  fire it, fixtures just under the threshold, and fixtures missing the fields it reads.
  Pure functions, so coverage is cheap here and wrong answers are most expensive.
- **Scoring — golden tests.** Whole feature trees with asserted scores, so tuning a
  weight shows every session it moved.
- **Registry completeness test** — enumerate the rule registry and assert every `type`
  has a frontend message template, so a new rule cannot ship rendering a raw id.
- **Worker — integration tests against a throwaway Postgres**: claiming, concurrent
  replicas, the failure path, backfill by date and by stale `rules_version`.
- **API — route tests against a seeded database**: filters, keyset pagination across page
  boundaries, auth rejection, the missing-dump path.
- **Frontend — one Playwright smoke test**: log in, filter, open a session, verdict
  renders, evidence zooms the charts.

## Future work

Explicitly deferred, and deferred in a way that does not require a rewrite:

- **Precomputed chart bundles.** If browser-side parsing proves too slow for large dumps,
  the worker emits a downsampled timeseries bundle next to the dump in MinIO and the
  detail page loads that instead. The worker already runs per dump; this is a second
  output, not a new pipeline.
- **LLM narrative panel.** `rtcstats_llm` stays a separate service the API calls over
  HTTP; observations from the rules layer make better input to it than a raw dump.
- **Side-by-side hosted analysis.** Because the dashboard tables mirror
  `rtcstats_analysis` / `rtcstats_observations`, the detail page can render rtcstats.com's
  verdict next to the local one for dumps that were forwarded.
- **Multi-tenant scoping.** Would need a tenant column; `rtcstats_user` and
  `rtcstats_conference` are free-text metadata, not identity.
- **Fleet-level trends.** A different product surface from post-mortem analysis.
